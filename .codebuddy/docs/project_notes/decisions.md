# 项目决策记录 (Architectural Decisions)

## [2026-01-28] - ADR-001: 使用 Dexie.js 替代 LocalStorage

**上下文**:
- LocalStorage 有 5MB 存储限制
- 文档可能包含大量图片的 Base64 数据
- 用户需要离线编辑能力

**决策**:
- 采用 Dexie.js (IndexedDB wrapper)
- 支持 50MB+ 存储空间
- 异步 API, 性能更优

**替代方案**:
1. LocalStorage (限制 5MB) ❌
2. IndexedDB 原生 API (过于复杂) ❌
3. Dexie.js (简洁 API, 良好的 TypeScript 支持) ✅

**后果**:
- ✅ 支持大量图片存储
- ✅ 异步操作, 不阻塞 UI
- ✅ 良好的浏览器兼容性
- ⚠️ 需要学习新的 API

## [2026-01-28] - ADR-002: 采用暴力覆盖算法处理章节重写

**上下文**:
- 用户可以多次生成同一章节
- 需要确保新生成的内容正确插入
- 避免内容冲突和混乱

**决策**:
- 实现暴力覆盖算法
- 定位当前章节, 查找边界 (同级或更高级标题)
- 清空中间所有内容块
- 插入新生成的 Block 数组

**替代方案**:
1. 追加模式 (容易造成重复) ❌
2. 合并模式 (复杂度高, 容易出错) ❌
3. 暴力覆盖 (简单可靠) ✅

**后果**:
- ✅ 逻辑简单, 易于维护
- ✅ 避免内容冲突
- ⚠️ 不可逆, 需要 Toast 提示

## [2026-01-28] - ADR-003: 无状态后端设计

**上下文**:
- 后端仅需负责导出功能
- 不保存用户数据
- 减少服务器存储成本

**决策**:
- 采用无状态后端设计
- FastAPI 仅接收 Markdown + 图片流
- 转换为 .docx 后返回, 清理临时文件

**替代方案**:
1. 有状态后端 (保存用户文档) ❌
2. 无状态后端 (仅导出) ✅

**后果**:
- ✅ 降低服务器成本
- ✅ 提高安全性 (不保存用户数据)
- ✅ 水平扩展容易
- ⚠️ 用户数据仅保存在本地

## [2026-01-28] - ADR-004: 使用 Tiptap + Custom Node Views

**上下文**:
- 需要灵活的编辑器
- 支持 Markdown 解析
- 自定义块级操作 (拖拽, hover)

**决策**:
- 使用 Tiptap (基于 ProseMirror)
- 自定义 Node Views (React)
- 实现独特的 UI 交互

**替代方案**:
1. Slate.js (学习曲线陡峭) ❌
2. Quill (自定义能力有限) ❌
3. Tiptap (灵活, 文档完善) ✅

**后果**:
- ✅ 强大的扩展性
- ✅ 良好的 Markdown 支持
- ✅ 活跃的社区
- ⚠️ 需要深入学习 ProseMirror 概念

## [2026-01-28] - ADR-005: 图片存储为 Base64

**上下文**:
- 用户可以离线编辑
- 需要快速导出
- 减少网络请求

**决策**:
- 图片转为 Base64 字符串
- 存储在 IndexedDB
- 导出时解码为临时文件

**替代方案**:
1. 上传到对象存储 (需要网络) ❌
2. Blob URL (刷新丢失) ❌
3. Base64 (离线可用) ✅

**后果**:
- ✅ 支持离线编辑
- ✅ 导出快速
- ⚠️ IndexedDB 空间占用较大
- ⚠️ 需要限制单张图片大小 (10MB)

## [2026-01-28] - ADR-006: 三个独立的 Dify API Key 配置

**上下文**:
- 大纲写作、正文写作、LLM 对话是三个独立的功能
- 使用不同的 Workflow，需要不同的 API Key
- 需要灵活配置每个功能的 AI 能力和模型

**决策**:
- 在 `useStore` 中存储三个独立的 API Key:
  - `apiKey`: 大纲写作 API Key (NEXT_PUBLIC_DIFY_OUTLINE_KEY)
  - `chapterApiKey`: 正文写作 API Key (NEXT_PUBLIC_DIFY_CHAPTER_KEY)
  - `chatApiKey`: LLM 对话 API Key (NEXT_PUBLIC_DIFY_LLM_KEY)
- 每个功能使用对应的 API Key 调用相应的 Workflow

**替代方案**:
1. 单一 API Key (限制灵活性) ❌
2. 动态配置 API Key (增加复杂度) ❌
3. 三个独立 API Key (最佳实践) ✅

**后果**:
- ✅ 每个功能可以使用不同的模型和能力
- ✅ 便于隔离和管理
- ✅ 支持不同场景的配置
- ⚠️ 需要配置三个不同的 API Key
